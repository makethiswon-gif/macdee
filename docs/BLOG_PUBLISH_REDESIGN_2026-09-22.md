## 1. 실제 비용을 원고에 붙이기

현재: 유료 응답은 `owner-briefings/blog-paid-operations/{id}/response.json` 에 usage 까지 통째로 보존되지만, **어느 원고의 것인지 연결이 없다**. 원고 라우트는 operationId 를 클라이언트에 돌려주지도 않는다(오류일 때만).

설계
- `blog_posts.ai_usage JSONB` (배열) 추가. 항목: `{stage, model, operationId, reused, input, cacheRead, cacheWrite, output, thinking, imageOutput, elapsedMs, at, kind}`. `kind` ∈ 원고 | 표지기획 | 표지원본 | 부분수정 | 재조판(무료).
- 각 유료 라우트(원고·기획·generate-design·부분수정)가 응답에 `usage` 항목을 실어 준다. 클라이언트는 원고 저장(`persist`) 때 함께 저장하고, 이후 단계는 `PATCH /api/admin/blog-posts/[id]` 로 append 한다. 서버는 `paidJsonRequest` 결과의 `reused` 를 그대로 넘겨 **재사용은 비용 0으로 기록**한다.
- 비용 = 토큰 × 코드 안 단가표(`lib/ai/pricing.ts`, 갱신일 명시). 화면에는 "추정(공식 단가표 기준) · 청구액 아님" 라벨. 이미지 모델 단가는 확인되지 않으면 토큰 수만 표시.
- 발행 화면 상단에 편당 합계 + 단계별 접이식, 관리자 목록에는 프로필별 월 합계. 실패한 호출(status≠2xx)도 기록하되 "과금 여부 미확인" 표기.
- 과거 로그 이관은 하지 않는다(원고 연결 정보가 없다). 9/22 이후 신규분부터 쌓인다.

## 2. 발행 화면 3단계

현재 흐름: 변호사 → 주제 추천(무료) → 원고 생성 → **자동 저장 → 자동으로 3장 이미지 생성** → 복사/저장. 새로고침하면 진행 중 배치는 사라지고, "저장 원고에서 이어서"로 원고만 복구된다.

### A. 기획·자료
- 변호사 + 주제(추천 카드 또는 직접 입력)만 있으면 시작. 나머지는 접힌 "선택 입력": 사건 메모, 참고 자료(URL·텍스트 붙이기), 변호사 관점 한 줄.
- **브리프 카드**(핵심 질문 / 결론을 가르는 조건 / 관점 한 줄)를 보여 주고 고칠 수 있게 한다. 값은 추천 라우트가 이미 주는 `topic`·`angle` 과 사용자 입력에서 채운다 — **추가 유료 호출 없음**. 비워 두면 모델이 정한다.
- 원고 생성 버튼 하나. 예상 비용을 옆에 작게.

### B. 원고 검수·확정
- 원고 생성 → 즉시 저장(`draft`) → 이 단계에서 멈춘다. **이미지는 만들지 않는다.**
- 좌: 본문 편집/네이버 미리보기 토글(현재 기능). 우: 검수 패널 — 편집 경고, 사실 확인 목록(§6), 브리프와의 일치(핵심 질문에 답했는가: 모델이 돌려준 question/thesis 표시).
- 부분 수정(§4)은 여기서만. 수정마다 버전이 쌓이고 되돌리기 가능.
- "원고 확정" 버튼 → `status: reviewed`(신규 값) → C로. 확정 후 본문을 고치면 다시 B로 내려오고 이미지 유효성 재판정(§4).

### C. 이미지·발행
- 표지 기획(통합 응답에 포함되면 무료, 없으면 별도 유료) → 표지 원본(유료) → 신뢰·상담 카드(무료, 표지와 **동시에**) → 저장 → 복사·zip.
- 카드별 상태(대기/제작/실패/저장)와 "이 카드만 다시", "표지 콘셉트만 바꾸기(유료 기획)", "문구만 다시 조판(무료)" 을 구분해 표시.

### 저장·이어하기
- URL에 `?post={id}` 를 고정하고, 단계는 `blog_posts.workflow JSONB {stage, briefing, planCacheId, productions:{type: productionId}}` 에 저장한다. 새로고침·다른 기기에서도 같은 자리로 돌아온다.
- 서버는 이미 결정적 ID(plan cacheId = 원고 해시+프로필, productionId = 기획+옵션 해시)로 재사용하므로, 클라이언트가 같은 요청을 다시 보내면 **추가 과금 없이** 결과를 받는다. 이어하기는 이 성질을 그대로 쓰고, 화면은 "복구 중(무료)" 을 명시한다.
- 중복 클릭: 진행 중 AbortController + 버튼 disabled(현재) 유지, 여기에 `workflow.lock {at, by}` 를 두어 다른 탭에서 같은 원고를 동시에 만들지 않게 경고.

## 3. 중복 AI 호출 줄이기 — 원고 응답에 표지 브리프 포함

현재 기획 호출이 실제로 쓰는 것은 표지 한 장의 **heading(1~2줄)·kicker·emphasis(강조 한 단어)·art{subject, scene, message, avoid}·alternateArt** 뿐이다(`three-card-renderer.ts:130`, `photo-generator.ts:27~38`). 스키마의 question/thesis/direction.alternatives/evidence/infographic 은 3장 세트에서 카드에 인쇄되지 않는다. 그런데 이걸 위해 원고 전체(4~5천 토큰)를 다시 보내고 3천 토큰의 JSON 을 받는다.

설계 — `blog-manuscript-v15`
- 출력 형식에 `===COVER===` 블록 추가(BODY·FACTS 뒤, 12줄 이내):
  ```
  heading: (8~24자, 줄바꿈으로 2줄까지)
  kicker: (분야 표제 6자 이내)
  emphasis: (heading 안의 한 단어, 없으면 빈칸)
  subject / scene / message / avoid / alternate_scene
  ```
- 서버가 `layoutRecipe`·palette·typography·brand 를 붙여 `ArticleVisualPlan` 으로 조립한다(지금 `planEditorialThree` 가 응답 뒤에 하는 일과 같음). 기획 모델이 결정하던 `direction` 은 이미 `lockDirection` 으로 프로필 값에 고정되므로 잃는 것이 없다.
- **독립 검증·독립 보존**: 원고(TITLE/BODY/FACTS)가 유효하고 COVER 만 깨지면 원고는 저장하고 `coverBrief: null` 로 두어, C 단계에서 기존 유료 기획 경로가 대신 돈다. 반대로 원고가 깨졌으면 COVER 는 버린다. 한쪽 때문에 전체를 재생성하지 않는다.
- 별도 기획 경로 유지: 불러온 옛 원고(COVER 없음), "표지 콘셉트만 바꾸기", 이미지 스튜디오 단독 사용.
- 품질 비교 스위치: `BLOG_COVER_SOURCE = manuscript | planner` 환경 변수. 표지 품질이 떨어지면 되돌린다. 비교는 같은 원고로 두 방식의 표지를 나란히 놓고 대표가 고른다(유료: 표지 원본 2장).
- 효과(추정): 편당 입력 −11k, 출력 −3k → Sonnet 기준 **−$0.05**, 시간 **−50초**. 원고 출력은 +200토큰.

덤으로 같은 원고 생성에서 받는 `question`/`thesis` 두 줄을 B 단계 검수 패널의 "이 글이 답하는 질문"으로 쓴다.

## 4. 필요한 부분만 수정

- 새 라우트 `POST /api/admin/claude-blog-edit` (Sonnet 5, effort **medium**, adaptive). 입력: `postId, scope, instruction`. scope ∈ `title | intro | paragraph:{n} | section:{h2 index} | closing`. 서버가 본문에서 해당 구간 + 앞뒤 한 문단 + 관련 FACTS 항목 + 문체 DNA 요약만 보낸다(전체 본문 아님 → 입력 1~2천 토큰). 출력은 교체할 구간 텍스트만.
- 클라이언트: 수정 전후 나란히 비교 → 적용/취소. 적용 시 `blog_posts.body` 갱신 + `body_versions JSONB` 에 이전 본문 push(최대 20). 되돌리기는 pop.
- 본문이 바뀌면: ① 사실 확인 목록의 각 항목을 "본문에 그 문장이 남아 있는가"로 재판정(있으면 상태 유지, 없으면 `stale`). ② `sourceHash` 가 바뀌므로 기존 이미지는 `imagesStale`. **발행(복사·zip) 버튼은 stale 이미지가 있으면 잠근다** — 지금은 경고만 뜬다.
- 재조판과 재생성 분리(이미 있는 `renderOnly`·`reuseProductionId` 경로를 UI 로 노출): 표지 문구·강조어·색 조정 → 기존 원본 사진으로 무료 재조판. 사진이 글과 안 맞음 → "콘셉트만 바꾸기"(유료 기획) 또는 "다른 장면(alternateArt)로"(유료 원본).
- 표지 문구가 본문과 어긋나는 판정: 표지 heading 의 명사가 새 본문에 하나도 없으면 "표지 문구 확인" 경고.

## 5. 입력·사고 비용

- **가장 큰 레버는 thinking 이다.** high vs xhigh 비교 시험: 같은 주제 3개 × 2 = Sonnet 6회(약 $0.8). 비교 항목은 §검증 참조. 결과 전에는 xhigh 유지.
- 프롬프트 정리(무료): 원고 시스템 프롬프트 6,100자 안에 "확인되지 않은 경력을 쓰지 않는다"류가 3곳, 강조 규칙이 2곳 중복. 법률 정확성·이미지 품질 제약은 그대로 두고 중복만 합치면 약 15% 준다.
- 캐싱: 순서를 [공통 규칙(고정)] → [변호사 블록: DNA·연락처 규칙] → [이번 글: 날짜·주제·최근 글 회피] 로 재배치하고 첫 두 블록 끝에 `cache_control` 을 둔다. 몰아 쓰는 날 2편째부터 입력 5천 토큰이 90% 할인. **정직한 기대치: 편당 $0.005~0.01.** 5분 TTL 쓰기는 1.25배, 1시간은 더 비싸므로(공식 문서 확인) 쓰기 비용이 첫 편에 얹힌다. 가치는 비용보다 "정리된 프롬프트"에 있다.
- `max_tokens` 16,000 유지. 실측 최대 출력 12,387 이라 여유가 필요하다.
- 유료 호출은 화면에 항상 "(유료)" 표기, 불확실 응답의 자동 재호출 금지(현행 `paidJsonRequest` 정책 유지).

## 6. 검수 — 사실 확인의 기록

- `blog_posts.fact_checks JSONB`: `[{claim, sourceUrl?, sourceNote?, effectiveDate?, status: unverified|verified|corrected|stale, checkedBy, checkedAt, bodyHashAtCheck}]`. 원고 생성 시 FACTS 목록으로 초기화(status unverified).
- B 단계 패널에서 항목마다 출처 URL/메모 입력, "확인" 버튼. **모델이 출처를 함께 낸 경우도 unverified** 로 시작한다(모델 생성 = 확인 아님).
- 본문 수정·재생성 시 `bodyHashAtCheck` 불일치 → 본문에 문장이 남아 있으면 유지, 없으면 stale. 재생성은 목록을 새로 만들고 옛 목록은 `fact_checks_history` 로 이동.
- 발행 버튼 옆에 "미확인 N건" 표시. 잠그지는 않는다(대표 판단) — 잠그기를 원하시면 설정으로.
- 검색·법령 API 연동은 이 단계에서 하지 않는다. 자료 첨부(URL·발췌)와 기록까지.
- 전송 최소화: 부분 수정·기획 호출에 전화번호·주소·경력은 보내지 않는다(현재 원고 프롬프트는 이름·사무소·연락처 규칙만 보냄 — 유지).

## 7. 챗지피티 기획과의 비교

| 항목 | 챗지피티 기획 | 제 판단 | 최종안 |
|---|---|---|---|
| 비용 표시 | 단계별 usage 를 원고에 연결, 추정/실측 구분 | 동의. 단, 원고 ID 연결이 현재 전혀 없어 스키마(`ai_usage`)와 라우트 응답 변경이 필요 | 채택 (§1) |
| 3단계 화면 | 기획·자료 → 검수·확정 → 이미지·발행 | 동의. 브리프 확인 단계가 유료 호출을 하나 더 만들면 안 됨 | 브리프는 추천 결과+입력에서 무료로 채움(§2A) |
| 원고 직후 이미지 자동 생성 중단 | 확정 후 시작 | 동의. 지금 원고 1편 재생성 때마다 이미지 3장 비용도 함께 나가는 구조 | 채택 |
| 통합 응답 | 원고 응답에 짧은 표지 기획 포함 | 동의. 3장 세트가 실제 쓰는 필드가 6개뿐이라 안전. 독립 검증·폴백 필수 | 채택 + 환경 변수 스위치(§3) |
| 부분 수정 | 범위 지정, 문맥 전달, 비교·되돌리기 | 동의. 버전 저장소(`body_versions`) 필요 | 채택 (§4) |
| 캐싱 | 공식 문서 확인 후 적용 | Sonnet 단가에서는 편당 1센트 안쪽. 우선순위 낮음 | 프롬프트 정리와 함께 P2 |
| high vs xhigh | 비교 가능하게, 검증 전 낮추지 말기 | 동의. 이게 진짜 절감 레버 | 유료 6회, 승인 후 (§5) |
| 검수 | 출처·시점·상태 연결, 검색 시스템은 나중 | 동의 | 채택 (§6) |
| 빠진 것 | — | 무료 카드 2장을 표지와 **동시에**(−32초), preflight·기획·생성의 시험 렌더 3중 중복 제거, stale 이미지 발행 잠금, 동시 탭 잠금, 낡은 테스트 정리 | 추가 |
| 위험 | — | 통합 응답으로 원고 출력이 길어지면 `stop_reason: max_tokens` 확률↑ → COVER 를 맨 뒤에 두고 12줄 제한. Vercel 300초 상한은 원고 최대 192초로 여유 | 반영 |

챗지피티 기획은 요구사항 목록으로 빠짐없고 방향도 맞다. 차이는 두 가지다. ① 돈이 어디서 나가는지 실측하면 **캐싱은 부차적이고 thinking 수준과 유료 이미지 자동 생성이 본질**이다. ② 화면 재편은 큰 공사인데, 서버는 이미 결정적 ID 로 재사용·복구가 되므로 **클라이언트가 postId 를 URL 에 고정하고 workflow 를 저장하는 것만으로 이어하기의 80%가 해결**된다. 재설계는 그 위에 얹는다.

## 8. 진행 순서 (모두 유료 생성 없이 개발·검증)

**P0 — 하루** (무료, 위험 낮음)
1. `ai_usage` 기록 + 발행 화면 비용 패널 (§1)
2. 원고 생성 후 이미지 자동 시작 제거, "원고 확정 → 이미지" 버튼 (§2B→C 관문만 먼저)
3. `?post=` 고정 + `workflow` 저장으로 이어하기 (§2)
4. 신뢰·상담 카드를 표지와 동시에, 시험 렌더 중복 제거 (S2·S3)

**P1 — 2~3일**
5. `blog-manuscript-v15` COVER 블록 + 독립 검증 + 폴백 + 스위치 (§3)
6. 부분 수정 라우트 + 비교/되돌리기 + stale 판정 + 발행 잠금 (§4)
7. 사실 확인 기록 (§6)

**P2 — 2일**
8. 3단계 화면 재편 + 모바일(390px) 검증 (§2 전체)
9. 프롬프트 중복 정리 + 캐시 배치 (§5)
10. high vs xhigh 비교 — **유료 6회, 사전 승인**

각 P 끝에 빌드·오프라인 테스트·발행 화면 브라우저 테스트(픽스처, 무료) 통과를 보고하고, 운영 배포는 대표 승인 후 커밋된 소스로 한다.

## 9. 검증 계획

- 단위: 통합 응답 파서(정상/COVER 손상/BODY 손상/잘림), 부분 수정 범위 추출, stale 판정, 비용 계산(재사용 0원).
